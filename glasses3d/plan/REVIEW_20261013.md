## 1. Verdict

- **There is no automation yet.** No code takes photos in and gives a GLB out. The job CLI
  (`python -m glasses3d job ...`), the Astra tool registry (WP2 stage D), delivery, the owner ledger and the
  end-to-end proofs (WP2 stages E-F) do not exist, and WP7 (Astra's instructions) is design only. The one Astra loop
  that has ever run in glasses3d is the WP6 facet lab, and it can only prepare Prada.
- **WP1-WP6 are built as separate tools, each tested on one or a few products.** None is connected to the others
  through an automation path. "Done" means: WP1, WP3, WP3b built and general; WP4 geometric half built (visual half
  never built, proof stale, 10 proof records still failing); WP5 accepted by eye on FT1119 only and havana-specific;
  WP6 accepted by eye on Prada only and Prada-wired.
- **The core infrastructure is good.** The Blender worker and its sandbox (no escape found), checkpoints, the money
  guard (no path found that spends past a run's cap by more than one mispriced request), the exporter and spec
  validator, the camera fitter, the temple builder and fit, and the arview renderer are careful, heavily tested code.
  The weakness is wiring and generality, not code quality.
- **Three of the tools fight each other when combined** (§4): the WP6 lab rebuilds from its start checkpoint on every
  edit (wiping seating or print done earlier), faceting replaces the temple's UVs (destroying a WP5 print), and WP4
  would bevel and groove an accepted crystal front. A job has to order them (temples, then seating, then print) and the
  lab has to learn to work on the job's current model.
- **Tests:** 2,594 of 2,671 Python tests passed in a loaded full run; after a low-load rerun exactly one real failure
  is left (a stale string since 2026-10-08, not a quality regression); arview 500/500 + 106/106 + type check clean.
  The suite depends on data outside `glasses3d/` (`automation/data`, `ar_v4`, OneDrive) that would make about 150
  tests skip or error on a fresh clone, and two seeing tests fail under parallel runs because of test order.

  "no output"): the WP5 bake tests start pools of `cpu_count - 2` processes inside every xdist worker.

## 5. Per work package

### WP1 arview (reviewers J, K)
- A fork of the live `ar/` renderer. Refusals are limited to the owner's §2 table; everything else is a warning plus
  fallback (verified throw by throw). Lens identification matches `g3d_host/lens_id.py` rule for rule. No product
  branches in the code.
- `arview capture` (14 / 36 / 133 posed images + 5 portrait) writes `report.json` and cross-checks every result with
  `spec.py`. `arview serve` is the owner's webcam page.
- Defects: default captures hide authored-size errors (P2, `eyewear-fit.ts:129-136`); shadows can drop silently while
  the report says applied; the crystal twin ignores a transmission texture; `npm run build` copies the live site's
  public catalog into `dist/`; the lockfile still names the package "ar".
- arview is hard-coupled to the live tree: it pins sha256 of `ar/public` files and requires `ar/public/mediapipe` to
  equal its own `node_modules` byte for byte, so a routine live-site asset update breaks `npm run build`.
- About 900 lines serve only live-site fps / hair-audit engineering (Measure panel, Hold & audit, exposure lock);
  they work and were kept.

### WP2 A-C session, seeing, money, loop (reviewers A, B)
- Worker + RPC + sandbox: static AST walk, restricted builtins, guarded import/getattr, an audit hook and a post-call
  file check. The earlier `str.format` escape is closed. No escape found.
- Money: worst-case reservation before every request, settlement from the response, tamper-checked ledger, retries
  forced to 0, the 59-row Prada replay settles exactly. A token-count failure (a network blip on the free count
  endpoint) ends a paid run; a crash mid-append makes reconcile fail; the implementation snapshot's `git diff`
  command line is ~23k of Windows' 32k limit and grows with the repo (about 260 more files will break it, after the
  approval is consumed).
- `run_astra` is generic (tools, instructions, brief, photos and scene hooks are injected), but its texts and timeout
  table still carry facet-lab wording. `ReviewLog.record_journal` is never called, so per-tool journals are not in
  run receipts. The heartbeat's `worker_cpu_s` is always null.
- `estimate.py` is calibrated on Studio code-writing runs (2,360 tokens/request growth); WP6 run 8 grew 4,950
  tokens/request. Recalibrate before the job CLI.

### WP3 exporter and validator (reviewer I)
- Correct axis/unit handling (mm → m baked into each mesh, `export_yup=False`); authored normals, sharp edges,
  clearcoat, textures and `partRole` survive. Not run by the session's export path (P2).
- `spec.py:633-646` fails orientation when the temples' hinge region is not above the lens centre; calibrated on 8
  browline/acetate models, it would fail a correct centre-hinged metal frame (P2, unproven on a real one).
- Renderable object types outside meshes/curves/text (geometry-node point clouds, hair curves) are dropped from the
  export without being listed as excluded.

### WP3b camera fitting (reviewer I)
- General in photo count and naming, multi-start Powell + contour ICP, priors for top / rear / top-oblique.
- Gaps (all P2 for new products): 6 view kinds only; one failing photo aborts every fit; the lens-optional loss is
  ported but never switched on; `fit_views` ignores per-photo matte modes that `compare` honours; the registration
  threshold PLAN asked the owner to confirm for WP5 was never recorded.
- The FT1119/Prada product registry and fixture names live in the production module `fit_views.py`.

### WP4 lens seating (reviewer F)
- Built: `seat_lens` (capture per frame type, V-bevel plus a live Boolean groove for crystal, nylor groove plus cord,
  rim sharpening), `hide_eyewire`, `check_lens_seating` (Blender and host share one core), `unseat` / `unhide`. No
  product constants in the core.
- Not built: the visual half (junction part-ID analysis on arview captures) and photo-derived hide ranges.
- "Complete and tested" overstates it: the last proof grades P3 34/40, P4 109/112 (+2 owner pending), P5 31/32,
  with 5 owner decisions open (metal junction 0.425 < 0.44, INVU 0.4489 < 0.45, FOLD cascades, the narrow-eyewire
  knife edge, `CORRECTION_AIM_MM`). The proof has been stale for 7 days because it hashes whole shared files.
- Defects: a rollback after a profile leaves the groove cutter / Boolean / cord behind (P2, `seat_bpy.py:1022-1038`);
  translucency detection differs between host and Blender; lenses with custom normals or rim UV seams refuse a
  profile.
- The accepted FT1123 crystal fails `check_lens_seating` (400/400 deep FAIL plus crystal overlap), so the check
  cannot be a delivery gate for crystal frames without an owner decision.

### WP5 photo print (reviewers G, H)
- Production path (`production.bake_print`: quilting, observed-slope boundary join, unscreened Poisson seam fix,
  optional AR level) is deterministic and refuses bad inputs. It reads a recorded step-0 report for region statuses;
  tier-1 multi-view mixing has never executed (nothing registered on FT1119).
- **P1 for any new product:** the donor rule assumes amber-to-brown pigment (`metal.py:91`, `PALE_MAX_THRESHOLD 0.85`
  on B/R). Measured on synthetic pigment: havana loses 2 % of photo pixels, blue 99.9 %, green 99.2 %, grey 88.6 %.
  Those parts become fill or flat grey.
- Other defects: `attach_print` paints 128-grey on parts left out by the cover rule (P2); `job_from_dir` ignores the
  basis colourway (P2); `Temple_L` vs `Temple_L.001` merge on the host (P2); one zero-area triangle crashes the
  layout (P2); a swallowed manifest error leaves a receipt naming a missing file (P2); calibration groups are
  hard-coded `brow` / `temple`.
- About 2,900 lines were the failed registration experiment (step 0) and about 5,200 lines of one-off proof and
  owner-sheet scripts; three runtime modules are copies of test modules that still run separately (a fix in one copy
  does not reach the other).

### WP6 faceted temples (reviewers C, D, E)
- Builder `g3d.temple/2`: closed 2-manifold, thickness and declared-shape refusals hold by construction; Blender
  build bit-equal to the host core. General for single-material acetate slab temples (outline single-valued along the
  arm, vertical inner face, no cut-outs); refuses multi-material and temples under 1 mm.
- Fit (`g3d/temple/fit.py`): sound joint least squares. **P2 verified:** when a read corner moves along the arm and
  an inner-table knot had snapped onto it, the fit writes t values the builder turns into a non-planar facet, and the
  builder refuses its own fit (`fit.py:2160`, `E_FACET_NOT_PLANAR`). Its test claims to cover this but never moves
  such a corner. The fit's position warning describes the design's node, not the fitted one.
- Lab: 7 strict tools, finish preconditions, variants, readings with an honest error model. `facet_finish` is
  accepted even when `validate_spec` fails (P2). Faceting drops existing UVs (P2). Four or more isolated facets are
  refused with an internal error (P2, `arrange.py:180-193`).
- Generalisable pieces for WP2 D: `readings.py` (multi-view triangulation), `sheets.py`, the finish-precondition
  pattern, `context_stubs`, the estimator mechanics.

### WP7 / WP8 (reviewer L)
- WP7_DESIGN and WP2_DESIGN §10 still name the retired v1 temple tools and gate G2 rows for them; WP7's size caps and
  rule-per-bullet style conflict with the WP6 v3 prompt. WP7 and WP2 stage D depend on each other (the registry
  carries the tool descriptions WP7 writes), so they must be built interleaved.
- WP8 as planned includes FT1119 (a print product), which WP7 forbids while the print gate is closed: WP8 needs the
  owner to open the print tools.
