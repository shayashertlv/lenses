# The constants ledger

Every number in this tree that a reviewer could reasonably ask "where did that
come from" has an entry here, with a **class**:

| class | means |
| --- | --- |
| `physics` | follows from geometry or mechanics; could not be otherwise |
| `derived` | computed from another number in this table, or from the template mesh itself |
| `published` | a figure from literature, transferred as a ratio |
| `measured` | this project measured it, and the report that did is named |
| `stated` | somebody chose it. No measurement decides it |
| `assumed` | a number the model needs, that nothing here can supply and nobody has looked up. Worse than `stated`: `stated` is a choice, `assumed` is a hole |

`npm run check:constants` fails if an exported constant has no entry. It does
**not** fail on the count of `stated` ones, and that is deliberate — v1's audit
got this exactly right: *"driving it to zero by writing better sentences is
exactly the dishonesty it exists to prevent."*

`assumed` was in use on the temple-reach row for some time before either the
legend above or the checker recognised it, which is exactly the drift this table
exists to catch: the checker counted it as nothing and the legend defined it as
nothing, so the highest-leverage number in the tree was in a class that formally
did not exist. Both now know about it.

Take the mix from the checker's own output rather than from a hand count — the
line it prints is the one that is guaranteed current, and the figure that used to
sit here (**24 stated, 16 published, 14 derived, 11 measured, 3 physics**) was
wrong on every number and missing a class. Two independent causes, both
corrections: the old line-regex counted the five-row legend above as data rows,
over-reporting every class by exactly one, and `assumed` was not counted at all.

As of 2026-09-01 (after the P1 campaign and the ledger's heading repair) the
checker prints, over 167 data rows covering 132 exported constants:

    75 stated · 42 measured · 24 derived · 22 published · 2 physics · 2 assumed

That replaces *59 stated · 25 measured · 22 published · 20 derived · 3 physics ·
1 assumed, over 130 rows covering 90 constants*, stamped 2026-08-24 and wrong on
all eight numbers by the time anyone read it — which had itself replaced *34
stated · 20 published · 17 measured · 15 derived · 3 physics · 1 assumed, over 90
rows*, correct on 2026-08-22 and silently wrong from the next commit onward.
Three generations of the same rot, in the paragraph whose subject is that rot,
and the line above will be the fourth. The instruction stands and is the only
durable part: **take the mix from the checker's output, not from here.** Run
`npm run check:constants`.

For comparison, v1's audit of its own tree found 196 constants of which 32 rested
on physics or geometry — six in seven were one person's number or arbitrary. The
difference is not that v2's authors are more careful; it is that v2 has a
synthetic population to measure against, so a number *can* be measured. Where it
still cannot be, it is in `docs/OPEN-QUESTIONS.md`.

**The checker's pipe defect is fixed.** An earlier version of this paragraph
recorded that a row whose `why` cell contained a literal `|` was silently
dropped — three rows were invisible to the gate for that reason.
`scripts/check-constants.mjs` now splits on unescaped pipes only, honours `\|`
as an escape, and treats an over-split row as a **loud failure** rather than a
silent drop, because a row that vanishes is a constant with no provenance
passing the gate. Write a literal pipe in a `why` cell as `\|`.

**A `## ` heading is a claim, and it is now checked.** Each one names the source
file that DECLARES the rows beneath it — comma-separated where one mechanism
genuinely spans two files, as `track/pnp.ts, track/tracker.ts` does, and
anything after an em dash is a topic gloss rather than a second path. A repeated
`| constant |` header with no `## ` above it inherits the heading above it;
there was one, under `testkit/synthetic.ts`, and it is merged now — a table that
inherits its heading is re-filed silently the next time a heading moves near it.
Nothing enforced any of this until 2026-09-01, and by then two headings named
files that do not exist — `core/compare.ts`, which is in no commit on any
branch, a stale `dist/src/core/compare.js` being all that is left of it, and
`fit/advice.ts`, renamed to `fit/score.ts` in `f9c9093` by the same commit that
rewrote 190 lines of this file — and twenty-five rows sat under a file that does
not declare them, eight of them `IDENTITY_*` rows filed under
`fit/frame-from-mesh.ts`, six of which name `track/identity.ts` in their own
prose. Nearly all of it was misfiled the day it was written rather than drifting
there, because a heading was the one thing `check-constants.mjs` never read.

It reads them now: a heading naming a file that does not exist, or a row whose
constant is declared in some other file, fails the gate. What it cannot judge it
skips rather than guesses at — a row titled in prose, a title naming two
constants at once, and any row whose declaration a line regex anchored at column
0 cannot find, which is what a bag field or a spec field looks like. It is also
row-driven, so a heading with no rows under it is never examined at all. Two
rows stay where no check can see them: `silhouetteStrips` band and temple reach
document a default parameter and a spec field rather than a named constant, and
they stay with the module whose behaviour they set, naming their declaring file
in their own title, which is all a reader has where no check can help. And cite
a row by its constant, not by line — the six line citations in
`docs/FIX-SPECS.md` were already half wrong before this paragraph pushed
everything below it down, and they are names now.

## 2026-08-22 — read this before quoting any `measured` row

`testkit/synthetic.ts` salted its capture RNG by `subject.id.length`. Every
generated id is three characters, so **every index-generated subject shared one
noise realisation**, and the population-by-camera grid held six distinct streams
rather than fifty-one. Every sweep that set a `measured` constant in this ledger
was run against that collapsed dimension: the spread each bracket describes was
geometry variation with the measurement noise frozen.

The seeding is fixed and the rows below have been re-derived where the sweep
could be re-run in this session. Where a row still rests on a bracket that has
**not** been re-run, it now says so in its own cell rather than carrying the old
number silently.

**Update, 2026-08-22 (the settlement campaign).** The single re-run above was
itself replicated: a campaign ran the contested sweeps at **five independent
seeds** and settled the rows that the one re-run had only unsettled.

changed direction — were set by that replication. **Neither has ever been a row

in dropped stash `1ce584f`, at the pre-settlement values 8-to-30 and 1.6 —
evidence that they were being kept, not provenance for the settled figures.
Do not go looking for them here, and do not write them back: a row for a
constant with no export is provenance for nothing that reads exactly like

One caveat travels with every campaign digit quoted below: **the campaign

## core/facemodel.ts

| constant | value | class | why |
| --- | --- | --- | --- |
| `NOSE_OBSERVED_FRACTION` | 0.40 | `measured` | The share of a scan's keyframes a well-observed nose accumulates as observation WEIGHT — the denominator `noseConfidence`'s `observed` term is graded against. `RegionQuality.observations` sums each frame's visibility (a continuous facing term in [0,1], gated at 0.05) and averages over the region's vertices, so it is not a frame count: a nose is oblique to the camera through most of the protocol by construction. Measured 2026-08-25 across 18 synthetic scans (4 subjects + both named extremes × the camera ladder, seed 11, framesPerBeat 12): `observations / framesUsed` ran **0.407–0.518, median 0.469**, and `framesUsed` was 24 — the keyframe count — on every one. Set at 0.40, just below the measured minimum, so a healthy scan clamps the term to 1 and it bites only on a nose that genuinely went unobserved; the margin is deliberate, since the synthetic protocol reaches yaw a real neck does not (Q13). **This replaced a bare `25`, and the replacement is the point.** The term is multiplicative, so the bare constant silently made confidence a function of the keyframe budget: when `KEYFRAME_DEFAULTS.count` dropped 48 → 24 on millimetre metrics that said nothing about this term, `observed` capped at 0.391–0.497 across those same 18 scans — **not one could reach half the term's range**, so every wearer-facing number was marked approximate and half of scans had their fit advice withheld with a sentence blaming the wearer. Normalising by `framesUsed` makes the term invariant to the keyframe budget, which is the property it needed and never had. |
| `TYPICAL_VARIANCE_FACTOR` | 1.9 | `measured` | The a-posteriori variance factor a healthy scan produces. `noseConfidence`'s third term is this over the scan's own factor. The *reason* for it is undisturbed: the detector's own sigma claim is routinely optimistic, and it replaced a term built on `quality.sigmaMm`, whose correlation with true nose error measures **−0.09** — absent, and slightly the wrong way round, because the worst camera geometry produces the *smallest* formal sigma. Set 2026-08-22 from the 5-seed replication (n=210, shipped pooled-iris config at keyframes=48; not re-measured at 24): per-seed medians 1.75 / 1.77 / 1.90 / 1.91 / 1.90, across-seed median of medians **1.90**, pooled median 1.86, pooled p90 5.52, band **1.44–8.33**. The upper tail is entirely phone-lap: per-geometry medians run eye-level 1.63, laptop-lid 1.83, **phone-lap 5.10** — the sigma claim is ~3× optimistic there — and the original 1.44–1.75 band described only the eye-level geometry. At 1.9 the agreement term reads 1.0 for median eye-level and laptop-lid scans and 0.37 for a median phone-lap scan. A consequence worth keeping from the earlier pass: the "real wearer measured ≈3.5 where synthetic gives 1.44–1.75" fingerprint that identified the `pixelScale` bug sits comfortably *inside* the honest synthetic range, so that inference would not be available today. The bug was real and the fix is verified independently; the fingerprint that found it was luckier than it looked. Re-checked 2026-08-23 on the merged tree after the keyframe-selector repair (same seeds, same shape: 14 subjects × 3 geometries × 5 seeds, n=210, keyframes=48, framesPerBeat 14, pooled iris): per-seed medians 1.80 / 1.82 / 1.95 / 1.96 / 1.94, median of medians 1.94, pooled median 1.90, pooled p90 5.63, band 1.50–8.90; per-geometry medians eye-level 1.67, laptop-lid 1.87, phone-lap 5.17. A uniform ≈+0.04 drift against the set-point digits above — the value 1.9 still sits at the pooled centre, and at 1.9 the agreement term still reads 1.0 / 1.0 / 0.37 for the three geometries' median scans. |
| `SCALE_DISAGREEMENT_EXPECTED_PCT` | 4.8 % | `derived` | The one-sigma of the DIFFERENCE between two rulers when both are behaving, not a tolerance anybody chose. The only pair that can occur is the wearer's PD against the iris: `IRIS.sigmaMm / IRIS.defaultMm` = 0.55/11.70 = 4.70%, against `PD_RULER.opticianSigmaMm` over the wearer's own PD — 1.11% at the 45 mm end of the admissible range, 0.79% at a typical 63 mm, 0.59% at 85 mm. In quadrature that is 4.74% to 4.83% across the whole range, so one number covers it and the iris term dominates so hard that 40 mm of wearer moves the answer by a tenth of a point. Sized from the RULERS rather than from what a downstream claim can tolerate, deliberately: the width verdict wants 1%, and a gate there would fire on most honest scans and be measuring the iris's ordinary scatter rather than a fault. Below this the two rulers are two rulers; above it the excess is real, one of them is wrong, and which one is not knowable from inside — so `scaleTrust` prices the excess as unmodelled error rather than choosing a winner. |
